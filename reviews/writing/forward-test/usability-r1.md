# academic-writing 规则工作流实际试用反馈 R1

测试对象和受审范围见 `review-r1.md`；规则表为 108 项，SHA-256 `aae85024984f65d16eebea25ebeaef4ca088e55820109a262f384dd9563a8e94`。这不是收到锁定版之后的最终 catalog 验收。

## 实际有用之处

- “首次阅读只用已知背景”让我把会读 `R_e(f)` 与知道风险含义区分，记录 Q02，而没有自动借用专业知识补成风险定义。
- LG03 的“谁／什么在改变”动作直接定位了 S4—S5 的“下降”省略。LG11 的比较标准动作又检查了它对两种鲁棒性要求的影响；可以共用一条发现，但保留不同判断理由。
- 规则要求接受理由，使 S5 的反例、S4 的“也可以要求”主语省略和允许环境量词得到明确接受依据，不需要为了显得认真把每句判成有缺陷。
- pending 与 fail 分开，能保留“前文可能已有解释”的真实边界。记录结论与正文结论分开，允许交付有用记录同时保持正文待修改。
- `init` 保留所有编号且不预设通过，有助于显示 105 项实际上没有执行。单元短引与文件摘要可自动复核，未把自动复核当成理解性验收。

## 本次不便使用的具体位置

1. **当前 catalog 不是可通过验证的版本。** catalog 命令退出 1，206 行诊断，主要为原句映射未完成。与技能根目录、表 SHA 和全文摘要已经一致，错误仍存在；这与父代理事先告知的映射完善中状态吻合。完整日志保存，没有用修改 checker 或删掉错误来制造通过。
2. **组合项需要分清通用约束与示例说明。** 当前 LG03 的子要求中包括「修改补出了为什么固定任务、考察什么，以及“整个模型族”指什么」和「它没有靠把三个短句简单拼成长句来解决问题」。两句是在解释特定改写例子，不应让只审读鲁棒性片段的代理去补“整个模型族”或宣称已改写。本次分别写不适用与触发条件理由；填表成本超过它们为本任务提供的额外信息。锁定版若将其明确记为 illustration，能降低机械执行风险。
3. **同一通过声明很容易过宽。** LG06 可以在修饰语作用域层面通过，S4 的“下降对象”却仍未解决。因此台账理由必须限定所核验的性质；只填“LG06 通过”会给人误以为句义已完整的印象。短引本身也不能替代这个说明。
4. **部分检查应保留粒度。** LG11 同时涉及当前两种评价标准、S2 三类变化和后文可能的多维分类。明确违反的一部分可 fail，没读到的分类和前置解释仍 pending；不能把总体 fail 写成所有子要求都被检查过。guide 的子项状态说明在这里必要。
5. **手工证据字段较多。** 一段五句也需要 scope.targets、artifacts、全文恢复位置、记录自身的不同恢复路径、每个组合子项的动作和证据。必要真实性信息有价值，但紧凑 Markdown 模板与完整 JSON 模板之间缺少一个小任务的完整填表示例。本次用了三个实际规则，其余模板 pending；没有为了填满所有条目扩大审读范围。
6. **项目表与通用表是两份工作。** 项目 writings.md 要求另外执行项目规则表，但这次父代理明确要求试用通用 catalog 且允许其余项 pending。本次只读取项目写作规范，不宣称执行了项目表。最终交付应保留这一边界，不把通用表的结构检查写成整套项目规范通过。

## 对工作流是否能用于实际审读的判断

当前 guide 与三个相关规则能定位具体对象歧义并留下可回查证据，也能约束没有发现问题的句子接受理由。此次试用不能证明所有条目覆盖完整、分类映射正确或正文全章合格。catalog 的当前校验失败必须和已完成的读者判断分别交付；锁定版就绪后可以保留 R1，再将已读证据重新绑定并重审发生变化的子要求。
