# 开发要求

本项目使用 Git worktree 隔离开发任务。每个独立任务在自己的工作目录和分支中修改、构建与验证；主工作区用于查看基线和集成已完成的变更。即使只修改规范或计划，也遵循此流程。

## 开始任务

1. 检查 `git status --short` 和 `git worktree list`，确认当前分支、已有任务与未提交修改。不得清理、覆盖或暂存其他任务的文件。
2. 继续既有任务时，复用该任务的 worktree；新任务创建独立 worktree 和分支。不得借用其他任务的目录，也不得让两个并行任务在同一 worktree 中写入。
3. 明确任务的基线提交与修改范围。新任务默认从本地 `main` 的已提交版本开始；用户指定分支或提交时按指定基线创建。需要远程最新内容时先获取并核对，不把本地 `main` 自动视为远程最新版本。
4. 分支默认使用 `codex/<task-name>`，目录使用已忽略的 `.worktrees/<task-name>/`，任务名采用英文小写和连字符。已有任务继续沿用原分支名，不为符合新命名约定而重命名。

在仓库主目录创建新任务的示例：

```bash
git status --short
git worktree list
git worktree add -b codex/theory-stability .worktrees/theory-stability main
cd .worktrees/theory-stability
git status --short
```

名称已被占用时，先确认是否属于当前任务；属于其他任务时另取名称，不使用 `-B` 或 `--force` 强行复用。worktree 从已提交基线创建，不会自动携带主工作区的未提交修改。若任务依赖这些修改，应先协调保存或集成，不能静默复制整个脏工作区。

## 修改与并行协作

- 创建后，所有编辑、资源生成、测试、构建、暂存和提交均在任务 worktree 中执行；使用工具时明确工作目录，确认路径属于该 worktree。不得回到主工作区实施日常开发。
- 每个 worktree 使用自身的 `build/` 和 `target/`。不得将这些目录软链接到主工作区或其他任务，也不得共用可写缓存、日志、临时图源或成品路径。同一 worktree 内的构建、监听和清理应串行执行，避免同时改写产物。
- worktree 隔离文件和暂存区，但仍共享 Git 对象、分支引用与默认仓库配置。不得切换、重置、删除其他任务的分支；修改共享 Git 配置或整理 worktree 时，应先确认对其他任务的影响。
- 并行任务应约定文件范围。章节入口、共享宏、文献库、索引词典、构建脚本和开发规范等公共文件需要协调修改；worktree 不能自动消除合并冲突。任务依赖另一任务的变更时，记录依赖分支或提交，避免重复实现。
- 各任务分别提交自己的源文件和对应成品。暂存前检查差异并按任务范围选择文件，不从其他 worktree 复制 PDF 或构建清单来充当当前任务的产物。

## 验证与集成

提交前遵循下文提交要求与 [LaTeX 与数学记号规范](latex.md)，在当前任务 worktree 内运行 `./build.sh all` 和 `./build.sh check-target`，确认七份 PDF 与 `target/.build-manifest.json` 对应当前输入。worktree 隔离不减免成品一致性检查，也不允许绕过提交钩子。

交付时说明 worktree 路径、分支、基线、变更范围和实际验证结果。未提交的成果应保留在原 worktree 并明确告知；不能让用户误以为变更已进入 `main`。

将变更集成到目标分支时，确认目标工作区没有会被覆盖的修改，并在该工作区停止构建或监听。集成操作串行进行；可使用专门的集成 worktree，但不能强行检出已经被其他 worktree 占用的分支。先合并源文件并解决冲突，再按最终源文件重新生成七份 PDF 和构建清单，运行 `./build.sh check-target` 及相应检查。PDF 和构建清单的冲突不能只靠选择某一分支版本解决；单个任务验证通过也不代表合并后的版本已通过验证。

## 收尾与清理

清理前检查任务 worktree 的状态、未跟踪文件，以及忽略目录中是否存在需要保留的成果，并确认提交已集成或已保存到可恢复的位置。未提交、未集成或仍被其他任务使用的 worktree 不得删除。

手工创建的 worktree 使用 `git worktree remove <path>` 清理，不直接删除目录，不用强制删除绕过脏工作区检查。由 Codex 管理的 worktree 使用对应归档功能，按其规则保存快照；需要保留的忽略文件应另行保存。确认分支已合并且不再使用后，才可用 `git branch -d <branch>` 删除任务分支，不使用 `-D` 丢弃未合并提交。

## 提交要求

提交历史应让读者看出每次修改的目的、涉及范围和验证结果。本项目统一使用英文类型与范围、中文描述；新提交遵循本规范，已发布历史仅在用户明确授权时重写。

### 消息格式

```text
类型(范围): 中文动作描述

需要时说明修改原因、关键取舍和影响范围。

验证：实际完成的检查及结果；未完成的检查应说明原因。
```

- 标题必须包含类型和范围，使用半角括号、半角冒号，冒号后留一个空格。
- 描述以具体动词开头，如“新增”“补充”“修正”“重组”“统一”“移除”，指出修改对象和结果，末尾不加句号。
- 标题尽量不超过 50 个字符；必要的术语、文件名和工具名保留原文。
- 不使用“更新内容”“优化细节”“修复问题”“WIP”等无法说明变化的标题，也不把多项无关修改塞进标题。
- 简单修改可仅写标题。跨文件重构、理论纠错和构建变更须补充正文，说明原因、影响与验证；不得把未执行的检查写成已通过。

### 类型与范围

类型按本次修改的主要目的选择：

| 类型 | 用途 |
| --- | --- |
| `docs` | 新增或改写正文、推导、示例、图解、参考文献、计划和规范 |
| `fix` | 修正错误公式、事实、引用、图示或程序行为 |
| `style` | 调整字体、配色、编号、边注和版式，不改变知识内容 |
| `refactor` | 调整目录、文件组织或宏结构，保持原有含义和功能 |
| `build` | 修改编译脚本、工具依赖、字体加载或构建配置 |
| `chore` | 仓库初始化、许可证及其他维护事项 |
| `revert` | 撤销已有提交；正文注明被撤销的提交及原因 |

书籍新增章节使用 `docs`，不使用表示软件功能的 `feat`。纠正错误优先使用 `fix`；仅补充讲解或改善表达使用 `docs`。恢复损坏的引用使用 `fix`，调整正常引用的显示样式使用 `style`。

范围采用稳定的英文小写名称，多个单词用连字符连接，不使用会随目录调整变化的章号。常用范围如下：

| 范围 | 对应内容 |
| --- | --- |
| `basics`、`theory`、`trustworthiness` | 机器学习基础、理论、可信性 |
| `models`、`paradigms`、`applications`、`systems` | 模型、范式、应用、系统各卷 |
| `book` | 全书结构或跨卷的统一调整 |
| `layout` | 模板与排版样式 |
| `latex` | LaTeX 构建工具及配置 |
| `specs`、`plans` | 开发规范、开发计划 |
| `repo` | 仓库、许可证及项目级维护 |

图像和文献若服务于某一主题，沿用该主题范围，不因文件存放在 `figures/` 或公共文献库中而另拆提交。新增范围前检查已有范围是否足够；确有需要时，在本表补充约定。

### 提交边界

- 修改、暂存和提交必须在所属任务的独立 worktree 内完成，流程见上文工作区要求。提交前确认工作目录和分支，只暂存本任务的变更；主工作区仅用于查看基线和串行集成。
- 一次提交解决一个可独立说明的问题。正文与对应图像、文献、章节入口应一起提交，使该次修改完整可用。
- 同一目标的连续润色可在发布前合并；可独立审阅的正文扩写、全书排版和构建变更应分别提交。
- 大范围移动文件时，尽量将纯结构调整与后续内容改写分开，便于确认内容没有丢失。
- 不提交 `build/`、临时文件、机器私有配置或凭据。提交前检查暂存区，避免夹带无关改动。
- 验证与修改匹配：正文、图像、版式和构建修改按 LaTeX 工程规范编译并检查 PDF；仅修改仓库说明或提交规范时，也须确认当前成品校验通过。

示例标题：

```text
docs(theory): 补充算法稳定性的泛化界推导
fix(basics): 修正训练集与测试集的符号引用
style(layout): 将边注编号改为按章重置
refactor(book): 按六卷结构重组章节目录
build(latex): 按字体文件路径加载中文字体
docs(specs): 统一提交消息格式与变更划分规则
```

### 历史整理与远程同步

日常发布后通过新提交修订，不为了措辞美观反复重写公共历史。用户明确授权重写时，先确认工作区状态并获取远程最新提交，保留本地备份分支或可恢复的归档，再进行整理。

整理后须核对最终文件树，确保除本次明确新增的修改外，原有文件内容和权限没有变化。更新远程时使用带预期远程提交值的 `--force-with-lease`，只更新目标分支；若远程已变化，应停止推送并检查新提交，不使用无条件强推覆盖。

### 提交前的 PDF 一致性

每次提交必须运行 `./build.sh all`，完成全部七份成品并生成
`target/.build-manifest.json`，再运行 `./build.sh check-target`。
`target/` 纳入 Git；将七份 PDF、校验记录及对应正文一并暂存。
版本化 `.githooks/pre-commit` 拒绝未暂存的正文输入，重新构建全部版本，
并核对暂存区 PDF 与当前正文和构建记录一致。若构建更新了成品，重新暂存
`target/` 后再提交；禁止绕过检查提交旧 PDF。
新克隆需执行 `git config --local core.hooksPath .githooks` 启用检查。
已有仓库的 linked worktree 通常共享此配置；应检查 `git config --get core.hooksPath`
是否为 `.githooks`，且当前 worktree 中钩子存在并可执行，不为单个任务随意改写共享配置。
各任务的成品在自身 worktree 内构建；集成后须依据最终源文件重新构建和校验，
不得直接采用另一分支的 PDF 或清单来解决产物冲突。
