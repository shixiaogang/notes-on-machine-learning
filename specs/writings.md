# 中文内容与写作规范

本规范适用于正文、章节大纲、示例、图表说明和边注。目标是让读者读懂问题、跟上推理，并知道结论可以用在哪里。后续 agent 必须据此组织内容、修订初稿和检查交稿质量。

## 作者定位与读者意识

以优秀计算机技术专栏作家和资深研发工程师的标准写作：既能把复杂问题讲清楚，也能对技术细节和适用条件负责。文字应逻辑严密、通俗易懂、行文流畅，保有耐心与人情味。专业程度体现在解释和论证中，不靠堆叠术语或宣称权威。

- 写作前确认本章读者已经学过什么、当前要解决什么问题、读完后应能解释或完成什么。以章节大纲和前文为依据，不默认读者掌握尚未介绍的知识。
- 面向具备本章前置知识、但初次接触当前主题的读者。需要额外背景时，给出足够的简短解释或准确的交叉引用。
- 以简洁、准确的现代中文写作。通俗表达仍须保留关键假设；为了亲切而虚构个人经历、读者反应或工程经验，同样不合格。

## 渐进式概念铺陈

- **问题先于名称。** 引入任何新技术、架构或概念前，先交代背景：当前要完成什么，已有做法遇到什么具体困难，或前文留下了什么尚未回答的问题。数学概念可以由一个待解释的现象、待证明的命题或推导需要引出，不必强造业务痛点。前文已经交代的问题可直接承接，无须重复铺垫。
- **核心术语出现后立即解释。** 首次出现时，紧接一句白话说明，交代它表示什么、在当前问题中起什么作用。英文全称、缩写和形式化定义不能代替这句解释，也不能用另一个未解释的术语来解释它。
- **从已知走向未知。** 先接住读者熟悉的对象或例子，再说明新概念与它的联系、增加的约束或解决的新问题，之后展开机制和推导。若一句话依赖多个尚未介绍的核心概念，应拆开并调整讲解顺序。
- 一个概念通常沿“问题与动机—白话解释或直觉—准确的定义—机制、推导或算法—示例—适用边界”展开。这是检查解释是否完整的思路，不是每节必须照抄的标题模板；定义和成立条件不能省略。
- 类比只在确实能降低理解难度时使用。说明熟悉场景中的对象分别对应什么，并在可能误导时指出类比的边界；随后回到技术对象本身。不要让读者先学会一个更复杂的比喻，也不要用比喻代替定义或证明。
- 不提前堆出尚未讲解的模型名、缩写和方法清单。确需预告后文时，说明它们将回答的问题，避免让读者误以为这些知识已是当前前提。

## 章节、段落与逻辑衔接

- 每章开头用具体问题引出学习目标，交代必要的前置知识和理解本章所需的路线。路线应说明各部分为什么相连，避免把目录扩写成“本章首先介绍……其次介绍……最后介绍……”。
- 开篇提出的疑问或技术挑战，必须在正文逐一拆解。属于本章范围的，给出明确回答；依赖后续章节的，说明本章已经解决到哪里，并给出后续入口，不能默默搁置。
- 每个段落推进一个中心意思。段首让读者知道当前在解释什么，后续句子提供原因、机制、证据或例子。若段落同时处理两个可以独立展开的问题，应拆开；若相邻段落反复表达同一意思，应合并或删减。
- 段落之间必须有可说明的关系：前一个结论带来什么新问题，哪个条件改变了，现有解释还缺哪一步。可以用一句承上启下的话明确这种关系；不能只加一个连接词掩盖内容跳跃。
- 正文中不用“首先、其次、再次、最后”充当机械式段落连接词。根据真实关系使用“由于……”“这意味着……”“但这一结论依赖……”等表达，也可以直接承接前句继续解释。不要把这些示例替换成新的固定句式。
- 只有因果或推导确实成立时才用“因此”“所以”“由此可见”；相关性、先后顺序和例子本身不能自动推出一般结论。转折也须说明与前文哪一点形成转折。
- 明确“它”“这”“上述方法”等指代的对象；同时出现多个模型、数据集或结论时，宁可重复名称，也不要让读者猜测。句子通常从前文已有信息接起，再落到需要展开的新信息。
- 结尾回到开篇的问题，收拢已经得到的答案、关键条件和仍未解决的部分。总结应提炼认识，避免逐节复述目录、逐句重复正文，或突然增加未经论证的新结论。
- 每章末尾必须设置独立的“本章小结”节，使用 `\section{本章小结}` 并添加语义化标签。新增、改写和结构重构都须保留该节，不得以其他小节的收束段落代替。
- 用连续段落讲解机制和推理。只有真正并列的事项、操作步骤或比较关系才用列表、编号或表格；算法步骤需要顺序时应明确编号。标题指出具体问题或内容，不用大量碎片化小标题替代论述。

## 自然中文与叙述语气

- **具体地说清谁做什么。** 优先使用主动语态和准确的动词，如“算法更新参数”，少写“参数更新操作得到了执行”。被动句在突出承受对象时仍可使用，不必机械消除。
- 删除不增加信息的套话，如“不可否认”“令人振奋”“众所周知”“值得一提的是”“总而言之”“旨在赋能”“具有重要意义”。若一句话去掉某个短语后意思不变，通常应去掉；若强调某项价值，应解释价值体现在哪里。
- 少用长串修饰语、抽象名词和“进行……的实现”一类绕行表达。说“用什么计算什么”“什么条件下出现什么结果”，比只说“实现能力提升”更清楚。避免不必要的拟人化。
- 长短句交替，以意思是否完整决定句长。一句话塞入多层条件、转折或结论时应拆开，并把条件放在它约束的结论附近；不要为了短句把紧密相连的推理切成一串碎片。
- 可以自然使用“我们”带领读者观察例子、作出假设或完成推导，用“你”提示读者尝试、比较或检查。定义、定理及客观结论保持中性、准确；不逐句添加代词，也不滥用“让我们一起……”等邀请语。
- 讲解复杂逻辑后，主动补上读者最可能卡住的一步，例如“为何可以这样变形”“这和刚才的概念有什么区别”“条件不满足会怎样”。可以直接解释，也可以偶尔设问，不把每段都写成自问自答。
- 不用“你一定会觉得”“相信大家已经明白”等话替读者下判断。避免“显然”“容易知道”“不难发现”掩盖推导缺口；应给出必要的一步、一个例子或一个引用。
- 亲切感来自解释到位和尊重读者，不靠感叹号、网络口头禅、刻意幽默或频繁打气。段落长度、开头方式和总结方式随内容变化，避免连续套用相同结构。

## 术语与排版约定

- 专业术语首次出现时写中文名称，并在括号内给出常用英文名称和缩写（如有），例如“经验风险最小化（empirical risk minimization, ERM）”。随后补上白话解释。后续使用统一的中文名称或缩写，不为词汇丰富而换用同义称呼。
- 引入术语前先搜索全书已有用法。同一英文术语不得随意更换中文译名，同一符号不得在未说明时改变含义；确有必要区分不同文献约定时，应明确说明对应关系。
- 对容易混淆的概念，指出区别落在哪个对象、条件或用途上，例如训练误差与泛化误差。不要用连续罗列定义代替比较。
- 中文正文使用全角标点；数学公式、代码、文件名和英文短语内部使用半角标点。
- 句末文献引文的标记放在中文句号之前，并使用 `\scite` 避免标记与句号跨行分离。
- 中文与行内公式、英文缩写之间不手工插入多余空格，由排版系统统一处理。符号、环境和版式分别遵循 [数学符号规范](latex.md)、[LaTeX 工程规范](latex.md) 和 [书籍样式规范](design.md)。

## 公式、示例与技术准确性

- 公式出现前，说明要计算、比较或证明什么，以及为什么需要这个表达式；公式中的新符号在出现前或紧随其后解释。核心公式之后说明结果意味着什么，以及它如何回答当前问题，不能只把公式逐字读一遍。
- 长推导按有意义的步骤展开，解释关键等式和不等式成立的依据。证明可以先说明思路，再展开细节；省略常规代数步骤时，仍须让具备前置知识的读者能够补齐。
- 优先沿用同一个小例子连接概念、公式和算法。只保留理解机制所需的细节；比较方法时，尽量固定任务、数据和评价口径，说明改变了哪个因素。例子承担新的解释任务，不能反复换说法而不增加认识。
- 示例应给出足够的输入、过程和结果，让读者能复核。示例中的符号必须与正文一致；人为设置的数值应明确标为假设或教学示例，不能冒充真实实验。必要时加入边界情形或反例，说明结论何时失效。
- 明确区分定义、定理、直觉解释、经验观察、工程惯例和作者观点。直觉帮助理解，例子展示某种情形，二者都不能代替一般性证明；采用简化假设时说明省略了什么。
- 陈述算法性质时写明成立条件；介绍模型时说明主要假设、计算代价和典型失效情形。不得把“在某些条件下可能有效”写成无条件保证。
- 比较“更快”“更好”“更稳定”时，交代相对于什么、用什么指标、在什么条件下成立。复杂度说明规模变量与计算对象，实验结论说明数据、设置和来源；没有依据的比较应删除或改成待验证的问题。
- 外部事实、历史信息、数据集描述和研究结论应引用可靠的一手资料；不要引用无法核验的转述。不虚构论文、作者、实验结果、数据或引文。不确定的信息应标记待核验，而不是猜测补全；未核实前不得当作已确认结论交稿。

## 交叉引用与正文边界

- 使用语义化交叉引用连接相关定义、公式、图表和章节，避免复制同一段解释。引用文献时说明其与当前论述的关系，不堆砌引用。
- 独立阅读某一节时，应能通过简短回顾或交叉引用找到必要背景；交叉引用不能替代当前推理不可缺少的解释。
- 正文引入图表时，说明读者应观察什么，以及观察结果支持哪一步论述。图注、表注交代对象、条件和主要读法，不能只重复标题。
- 核心定义、关键推理和阅读所必需的条件必须留在正文。边注用于补充背景、来源或延伸信息，不能要求读者不断跳到边栏才能跟上主线。

## 改写示例

以下示例展示修改方向，不是供各节重复套用的句式。示例中的专业术语在正式正文首次出现时，还须按前述约定补充英文名称。

### 从具体问题引出概念

不合格：

> 经验风险最小化是机器学习中的重要原则，具有广泛的应用价值。

改写：

> 同一批训练样本上，不同模型会给出不同的预测。要从候选模型中作出选择，我们需要先约定如何比较它们的错误。可以用损失函数为每次预测的错误计分，再计算模型在训练样本上的平均损失。在候选模型中选择这个平均损失最小的模型，就是经验风险最小化：按训练样本上的平均损失来选择模型。

这段文字先交代选择模型的困难，再引入比较准则和名称。后文仍需给出损失函数、候选范围及最小值存在等条件，不能把这段直觉说明当成完整定义。

### 让前一步自然引出后一步

不合格：

> 首先介绍训练误差。其次介绍测试误差。最后讨论泛化能力。

改写：

> 训练误差反映模型在参与训练的样本上表现如何。模型的参数已经根据这些样本调整过，因此这个结果还不能直接回答它面对新样本时会怎样。要考察这一点，我们需要另留一批不参与训练和调参的测试样本，并明确它们与未来数据的分布关系。

这里由已有指标的局限引出新的评价需要，读者能够理解为什么要继续讨论测试，而不只是知道下一个标题是什么。

### 补上关键依据，照顾读者的疑问

不合格：

> 显然，较小的训练误差并不意味着较小的泛化误差，这一点是不难理解的。

改写：

> 一个分类器可以记住每个训练样本及其标签，却对未见过的输入一律给出同一个类别。只要训练样本的标签不冲突，它就能在这些样本上全部答对；但对新输入，这种做法仍可能频繁出错。这个反例说明，仅凭训练误差小，还不能判断模型在新数据上也表现良好。

反例补出了原句省略的理由。“全部答对”所需的条件也同时写出，便于读者检查论证。

## 写作与修订流程

1. **写前准备。** 阅读相关大纲和相邻内容，列清本次要回答的问题、读者已有知识、需要引入的概念及依赖关系。查找已有术语、符号和引用，选择能贯穿讲解的例子。这些是工作笔记，不必全部写入正文。
2. **完成连贯初稿。** 按问题推进解释，让定义、公式、例子各自解决一个具体的理解障碍；发现前置知识缺失时及时补齐，避免用术语清单占位。
3. **检查逻辑。** 用一句话概括每段的作用，连起来看能否形成推理主线；核对开篇问题是否得到回答、相邻段落是否有跳步、结尾是否超出正文支持的范围。
4. **检查技术。** 复核定义、条件、符号、公式、示例数值和引用，检查类比与简化是否造成误解。先修正论证，再润色句子。
5. **检查语言。** 按自然朗读的节奏通读，修改拗口长句、含混指代和模板化过渡，删去空话、重复预告与重复总结。删减后仍须保留必要的解释和条件。

短小修改可以合并检查过程，但不能跳过相关检查。自查用于修订实际文字，不必把检查过程、规则名称或合规声明写进书中。

## 交稿前自查

- [ ] 读者能说明本节要解决什么问题，以及它为什么接在前文之后。
- [ ] 新概念有动机，核心术语首次出现后有白话解释，所依赖的知识已经介绍或给出入口。
- [ ] 每段有明确作用，段落之间的因果、条件、递进或转折真实成立，指代清楚。
- [ ] 复杂推理没有靠“显然”跳过关键步骤；公式、示例和文字能互相对应，必要条件没有藏在边注中。
- [ ] 同一概念的名称、缩写与符号一致；事实、比较和引用可以核验，直觉、假设与结论的边界明确。
- [ ] 语言具体、直接，句子节奏自然，没有空泛赞誉、机械串联、重复总结或刻意制造的亲切感。
- [ ] 开篇问题已有明确回应，结尾准确说明已解决的部分及适用边界，没有夸大结论。
- [ ] 本章末尾设有独立的“本章小结”节，未省略或并入其他小节。

发现未满足的适用项，必须修改后再交稿。文字检查不能用“编译通过”替代；涉及 LaTeX 内容或版式的修改，还须按工程规范完成编译与 PDF 检查。

## 参考写作指南

以下资料用于补充方法；上文是结合本书中文教材场景制定的规则。英文文档中的代词偏好、句长建议等不直接作为本书的硬性格式要求。

- [Google Technical Writing — Audience](https://developers.google.com/tech-writing/one/audience)：围绕读者已有知识与所需知识之间的差距安排解释。
- [Google Technical Writing — Paragraphs](https://developers.google.com/tech-writing/one/paragraphs)：段落保持单一中心，开头明确方向，控制过长和过碎的段落。
- [Google Technical Writing — Self-editing](https://developers.google.com/tech-writing/two/editing)：从读者视角重读初稿，通过朗读与复审发现表达障碍。
- [Google Developer Documentation Style Guide — Voice and tone](https://developers.google.com/style/tone)：采用自然、尊重读者的语气，避免夸张、说教和过度口语化。
- [Microsoft Writing Style Guide — Use simple words, concise sentences](https://learn.microsoft.com/en-us/style-guide/word-choice/use-simple-words-concise-sentences)：选用具体而准确的词，删去冗余，并保持术语一致。
